# 项目全量文档生成


## 目标

- 在当前目录中生成一份完整、详尽、可持续维护的项目总文档，而不是只给出摘要。
- 先通读项目已有文档、源码、配置和构建测试脚本，再落笔写文档，避免凭局部印象猜测。
- 必要时搜索补足框架、协议、标准、外部依赖或版本行为的准确信息；优先官方文档、一手规范和上游资料。
- 最终文档要能让新接手项目的人系统理解功能、架构、模块关系、关键实现、运行方式和边界条件。

## 典型触发

- "帮我完整理解这个项目并生成详细文档"
- "把整个仓库读一遍，在当前目录输出完整项目说明"
- "为这个代码库生成一份事无巨细的技术文档和架构图"
- "通读项目代码和文档，产出完整的实现说明与 Mermaid 图"

## 不触发场景

- 只需要简短总结、快速导览或单文件解释。
- 只需要修改代码、修复缺陷或添加功能，但没有要求生成完整项目文档。
- 只做局部模块说明，不要求覆盖整个项目。

## 工作流

### 生成前硬约束

- 起草前按读者任务和事实证据筛选表达；保留本 skill 要求的全量技术理解、详尽实现说明、章节结构和图表，不把语言清理变成摘要化。
- 规则同时约束文档、给用户的进度消息和最终说明。进度只报告必要的实际状态、阻塞和需用户决定的事项；交付时给出成果或位置，不用认同、承诺、泛泛免责或自检叙述代替成果。
- 可查事实先读源码、配置、文档或核实外部依据，不用笼统“不确定”回避调查。只对影响正确性、关键结论或交付范围且无法自行核实的问题追问，能继续的部分继续完成。
- 按语义清除过程泄漏、无源否定、无端假设、无实际任务依据的预防式前提、虚构读者预设/稻草人、无端转折、泛泛免责、无关未知清单，以及无必要的确认、审批或重复审查；换词不算修复，词面命中也不是删除理由。
- 仅对纠正、否定或对比句追问“读者为何会有相反预期”；普通正面事实无需消除误解。保留有证据且影响理解的限制、真实风险、关键事实缺口、用户要求的比较和结论必要边界，写清具体影响，不删掉正常技术条件或学术边界。
- 本 skill 可独立使用，不要求安装其他 skill 或执行调用框架的 review、QA 流程。

### 1. 建立全量上下文

- 优先枚举并阅读当前项目已有的文档、README、设计文档、接口文档、部署文档、测试文档、脚本说明和配置样例。
- 系统检查源码目录、入口文件、核心模块、依赖声明、构建脚本、测试目录、CI 配置、容器与部署配置、数据库或迁移脚本。
- 识别项目边界：对外接口、内部模块、外部依赖、数据流、控制流、运行时依赖、环境变量和部署形态。
- 在大型仓库中先建立模块地图，再逐层下钻到关键实现，避免只看零散文件。

### 2. 生成文档前先完成技术理解

- 为每一项主要功能建立"功能 → 入口 → 核心模块 → 关键数据结构 → 关键流程 → 输出结果"的理解链路。
- 对关键代码做解释，不只说明"做了什么"，还要说明"为什么这样做""依赖什么前提""可能的边界条件是什么"。
- 识别核心抽象、基础设施层、领域层、接口层、任务调度、数据访问层、消息或事件流，以及它们之间的调用和依赖关系。
- 如果存在框架约定、元编程、代码生成、动态路由、插件系统或反射注册机制，要把这些隐性机制单独解释清楚。

### 3. 在当前目录生成完整文档

- 默认在当前目录创建或更新一份单一的、可直接阅读的完整 Markdown 文档；若用户未指定文件名，使用清晰且稳定的名称，例如 `PROJECT_FULL_DOCUMENTATION.md`。
- 文档默认覆盖整个项目，不写成流水账或扫描结果清单，而是组织成结构化的技术说明书。
- 如果项目已经有成熟文档体系，仍要在当前目录产出一个能独立阅读的总文档，并在文中说明与现有文档的关系。

## 文档内容要求

### 必须覆盖的主题：包括但不限于以下：

- 项目概览：项目目标、解决的问题、主要能力、目标用户或服务对象。
- 功能全景：列出整个项目的主要功能单元，并逐项说明其实现方式与技术细节。
- 代码详解：解释关键模块、关键类、关键函数、关键流程、重要数据结构、配置入口和异常处理路径。
- 架构解释：说明整体架构风格、分层方式、模块边界、依赖关系、数据流和控制流。
- 运行机制：说明启动流程、初始化流程、请求或任务处理流程、后台任务、定时任务、消息处理或异步机制。
- 配置与依赖：说明环境变量、配置文件、第三方依赖、外部服务、数据库、中间件和关键版本约束。
- 构建与测试：说明构建方式、测试结构、运行命令、发布或部署相关流程。
- 边界与约束：说明已知限制、默认假设、失败路径、兼容性要求和潜在风险点。

### Mermaid 图要求

- 至少提供一张整体架构图，展示主要模块、外部系统和核心依赖关系。
- 在适合的情况下补充模块关系图、请求处理流程图、数据流图或部署图。
- 使用 Mermaid 语法，保证图和正文术语一致，节点命名清晰，不使用含糊缩写。
- 图必须服务于理解，不为了凑图而画空泛框图。

## 写作文风与质量要求

- 目标是"事无巨细的详尽解释"，但仍要保持结构清晰、术语统一、章节边界明确。
- 不只罗列文件名；要把代码组织、职责分工、调用关系和关键实现讲透。
- 对复杂代码路径给出分步骤解释，必要时用小段伪代码或流程描述帮助理解，但不要把整段源码大段复制进文档。
- 明确区分已经从代码或文档中证实的信息，与基于上下文做出的合理推断；推断要显式标注。
- 若信息不足以得出确定结论，继续读代码、读文档、执行命令或搜索检索，不要仓促下结论。
- 对仍无法核实的关键缺口，说明它具体影响哪项解释或操作；不罗列无关未知项，不将所有已核实结论降格为猜测。技术选型动机只有有依据时才写为事实，否则标明是推断。

## 推荐文档结构

1. 项目概览
2. 仓库结构与模块地图
3. 整体架构设计
4. 主要功能与实现详解
5. 核心代码路径解析
6. 数据模型、状态流转与外部依赖
7. 配置、构建、测试与部署
8. Mermaid 架构图与流程图
9. 关键约束、风险与维护建议

## 领域交付物检查清单

交付前做与文档规模相称的读回检查，不额外假定存在调用框架，也不为本 skill 无条件追加 review、QA 或审批流程。

- 已阅读整个项目中与理解全貌相关的现有文档和代码，而不是只看少数文件。
- 已在当前目录生成完整详细的 Markdown 文档。
- 已覆盖功能实现方式、代码技术细节、架构解释和 Mermaid 图。
- 已让文档达到新读者可据此快速建立全局理解的程度，而不是停留在摘要层面。
- 已读回实际成稿，核对关键事实依据、命令、路径、链接、章节覆盖和 Mermaid 图与正文的一致性；没有把未执行的测试或未验证的行为写成验证结果。
- 已按生成前硬约束检查文档及待发送说明，没有功能异常句，也没有误删必要细节、关键缺口或真实边界。

将读回作为内部模拟 hook：候选文本 → 语义与事实检查 → 命中则实际修改文件或待发正文 → 读回复查 → 无未处理命中才可交付。命中即未完成；只在回复中说要修改、列建议或许诺下一轮处理均不能放行。检查用于定点修补，不另起无关扩写或外部审查流程，也不把内部自检记录展示给用户。
