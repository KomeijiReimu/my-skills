# Create README

## 目标

- 生成结构清晰、信息充分、易于阅读且适合开源项目展示的 `README.md`。
- 先完整理解项目和 workspace，再决定写什么；调查可以全面，README 输出必须有选择。
- 让第一次接触项目的外部读者在没有看过聊天、提交历史、工作笔记或旧稿的情况下，独立判断项目用途并完成关键操作。
- “完整”表示覆盖读者完成主要任务所需的信息，不表示罗列所有已发现的技术事实。

## 核心原则

### 1. 把源材料与最终 README 分开

- 将用户消息、旧 README、代码审查结果、开发说明和调查发现视为源材料，不直接当作成稿。
- 从源材料中提取可验证的项目事实、读者任务和必要约束，再重新组织为独立可读的 README。
- 用户在对话中问过某件事，不代表 README 必须回答它；只有目标读者也需要该信息时才写入。
- 不把“为什么这样写”“这次改了什么”“之前哪里不对”等写作过程带入 README。

### 2. 全面调查，选择性输出

- 审查整个项目和 workspace，包括现有文档、入口、源码、依赖声明、配置、脚本、测试、示例和发布方式。
- 全面调查用于保证准确性，不用于扩大 README 篇幅。
- 不因发现某个实现细节就自动写入 README，也不因没有找到某项内容就主动声明项目不具备它。
- 无法从项目证据确认的功能、平台、性能、兼容性和使用场景不得猜测。

### 3. 以读者任务决定内容

起草前明确：

1. 主要读者是谁，例如最终用户、首次安装者、库调用者、部署人员或项目评估者。
2. 读者打开 README 要完成什么，例如判断是否适用、理解主要能力、完成最短成功路径、找到必要配置或避开重要风险。
3. 哪些深入内容应放入专用文档，而不是展开在 README 中。

README 常见职责包括：

- 说明项目是什么、解决什么问题。
- 展示已验证的主要能力和适用场景。
- 提供最短可运行或可使用路径。
- 说明关键配置、典型用法和会影响结果的重要限制。
- 引导读者前往更深入的 API、架构、部署或贡献文档。

README 通常不承担：

- 逐文件代码解释或完整架构档案。
- 开发日志、审查报告、修改说明或聊天答复。
- 与当前项目无关的通用技术科普。
- 只有维护者才关心的内部容错和实现细节。

## 内容准入门槛

每个标题、段落、列表项和提示都必须依次通过三道门槛。

### A. 证据门槛

- 内容由源码、配置、脚本、测试、已有项目文档或用户明确提供的项目事实支撑。
- 文件路径、命令、链接、配置名、环境变量、平台支持和版本要求均已核验。
- “未找到”不等于“确定不存在”。证据不足时继续调查、向用户确认或省略。
- 不虚构功能、性能结果、兼容性、路线图或使用场景。

### B. 读者价值门槛

内容至少满足一项：

- 帮助目标读者判断项目是否适合自己。
- 帮助读者完成安装、运行、配置或典型操作。
- 解释完成操作所需的关键概念。
- 防止高概率或高后果的真实错误。
- 说明会实际改变使用结果的重要边界。

仅仅“技术上正确”不是入选理由。对每段执行删除测试：

> 删除后，目标读者是否更难作出决定、完成操作或避开实际风险？

如果答案是否定的，删除、压缩或移出 README。

### C. README 位置门槛

- 首次采用和首次使用所需的信息放入 README。
- 完整 API、深入架构、复杂部署、贡献流程和维护细节放入专用文档，并在必要时提供链接。
- 内部实现细节只有在直接影响用户操作或结果时才保留。
- 不创建 `LICENSE`、`CONTRIBUTING`、`CHANGELOG` 等专用文件已有职责的重复章节。

## 语义级废话防护

不要依靠禁用词表。判断一句话在文档中的实际功能，而不是只看它用了什么词。

### 必须清除

- **对话残留**：回应用户曾经问过的问题、引用“前面”“上面”“按你的要求”等上下文。
- **修改残留**：说明旧稿哪里不准确、本次补了什么、为什么采用某种写法。
- **调查残留**：描述“检查后发现”“经过分析”“仓库中没有找到”等工作过程。
- **作者备忘**：解释内容选择、提醒后续作者、保留内部 TODO 或审阅意见。
- **无关否定**：主动否认一个读者没有合理理由期待、且不影响实际使用的事物。
- **防御性辩解**：为技术选型、缺失文件或项目定位回应一个 README 中从未出现的质疑。
- **事实堆积**：把内部容错、低层实现、未来兼容和边缘行为写入 README，只因为它们存在。
- **空泛宣传**：使用“强大、现代、革命性、无缝、易于使用”等无法帮助读者判断的套话。
- **凑章节内容**：为了模板完整而解释项目不存在的部署方式、接口、依赖或文件。

换掉触发词但保留同样语义仍然不合格。审查必须识别句子的功能，而不是寻找固定短语。

### 否定信息的合法条件

否定句并非一律删除。只有同时满足以下条件时才保留：

1. 读者有合理理由预期相反行为。
2. 该差异会影响安装、数据、安全、兼容性或采用决策。
3. 项目证据足以支持该结论。
4. 文中说明了具体后果或可执行的替代方案。

优先正面陈述项目实际做法。不要为了显得全面而主动列举项目不做什么。

## 正反例

示例用于说明判断方法，不是固定句式模板。

### 对话与过程隔离

- 反例：`按你的要求，我们补充了 Windows 安装方式。`
- 正例：`Windows：运行官方 Python 安装程序并启用 Tcl/Tk 组件。`
- 理由：读者需要安装方法，不需要知道它来自哪次对话。

- 反例：`检查项目后发现它使用 SQLite。`
- 正例：`项目使用 SQLite 存储本地数据。`
- 理由：直接交付项目事实，不汇报调查过程。

### 无关否定与重要限制

- 反例：`本项目没有移动端应用。`
- 正例：省略整句。
- 理由：如果目标读者没有合理的移动端预期，该信息不帮助使用项目。

- 合理：`数据仅保存在内存中，进程重启后会丢失。`
- 理由：该限制会直接影响数据安全和采用决策。

- 合理：`服务不提供身份认证；暴露到公网前请配置反向代理认证。`
- 理由：它指出高后果风险并给出行动方案。

### 回答真实任务，而非解释缺失

- 反例：`项目没有第三方依赖，因此不需要 requirements.txt。`
- 正例：在安装章节直接列出经过核验的运行要求和启动命令。
- 理由：读者要知道如何运行，不需要作者解释某个文件为什么不存在。

- 反例：`Windows 不使用 AppData，而是采用另一套路径。`
- 正例：`Windows 配置目录：<经过核验的实际路径>。`
- 理由：优先给出操作答案，只有旧路径会造成真实迁移风险时才补充对比。

### 粒度与位置

- 反例：在 README 中逐个解释内部类、私有函数和完整调用链。
- 正例：概述用户可见能力，并链接到架构或 API 文档。
- 理由：有价值的信息也要放在正确的文档位置。

## 工作流

### 1. 检查项目

- 阅读整个项目和 workspace 中与用途、功能、运行、配置和使用有关的材料。
- 确认项目类型，例如 CLI、库、桌面应用、Web 服务或模板仓库。
- 核验所有准备展示的命令、路径、配置和示例。
- 找到真实存在且适合展示的 logo 或 icon 时，将其用于 README 页头。

### 2. 建立 README 契约

- 写明主要读者、首要任务、最短成功路径和 README 边界。
- 根据项目形态选择章节，不把所有项目强行套进同一模板。
- 先列候选内容，再通过三道准入门槛筛选。

### 3. 组织内容

优先采用渐进披露：

1. 项目是什么、解决什么问题。
2. 已验证的主要能力。
3. 最短成功路径。
4. 典型用法。
5. 必要配置和关键限制。
6. 指向深入文档的链接。

只创建项目实际需要的章节。避免空章节、占位内容和为“完整”而加入的无关说明。

### 4. 起草 README

- 使用 GFM（GitHub Flavored Markdown）。
- 仅在确实改善重要提示或风险表达时使用 GitHub admonition。
- 克制使用 emoji，保持简洁直接。
- 使用具体、可验证的能力描述，避免宣传套话。
- 让标题、命令、示例和术语前后一致。

可参考以下 README 的结构、语气和表达方式，但不能复制其项目事实，也不能强制套用其结构：

- https://raw.githubusercontent.com/Azure-Samples/serverless-chat-langchainjs/refs/heads/main/README.md
- https://raw.githubusercontent.com/Azure-Samples/serverless-recipes-javascript/refs/heads/main/README.md
- https://raw.githubusercontent.com/sinedied/run-on-output/refs/heads/main/README.md
- https://raw.githubusercontent.com/sinedied/smoke/refs/heads/main/README.md

### 5. 冷读审查

假设读者没有看过聊天、旧 README、提交记录或作者笔记，逐段检查：

1. 这段服务哪个目标读者？
2. 它回答什么真实问题？
3. 它依据哪个项目事实？
4. 删除后会损害哪项决定、操作或风险认知？
5. 为什么它应放在 README，而不是其他文档？

无法给出具体答案的标题、段落或列表项必须删除、压缩或移出 README。

## 交付门槛

交付前必须全部满足：

### 事实

- 项目特定事实均可追溯到已检查的代码、配置、测试或文档。
- 路径、链接、命令、配置名、环境变量和平台声明已核验。
- 未把“没有找到”写成“确定不存在”。
- 没有猜测功能、兼容性、性能、路线图或使用场景。

### 读者价值

- 首次读者能快速理解项目用途和主要能力。
- 最短成功路径完整且命令顺序明确。
- 每个章节都服务真实读者任务，没有为了模板而存在的内容。
- 深入内容被压缩或链接到合适文档。

### 成品隔离

- 对话回应、修改说明、调查过程、审阅口吻、作者备忘和内部 TODO 为零。
- 无实际后果的否定说明和防御性辩解为零。
- 没有解释读者未曾期待的缺失文件、功能、依赖或技术选择。
- README 能在脱离所有写作背景后独立成立。

### 原有质量要求

- README 结构清晰、信息充分、吸引人且易读。
- 内容简洁直接，emoji 使用克制。
- 使用 GFM；admonition 仅用于有明确价值的提示。
- 不重复 `LICENSE`、`CONTRIBUTING`、`CHANGELOG` 等专用文件职责。
- 真实且合适的 logo/icon 已在页头使用；不存在合适资源时不虚构。
