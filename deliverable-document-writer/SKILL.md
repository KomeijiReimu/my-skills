# 交付文档写作

## 概述

把工作材料整理成一份可以独立阅读、可以直接交付的正式文档，让外部读者在没有看过对话、笔记、修订记录或旧稿的情况下，也能顺畅理解内容。

## 工作流

### 1. 先确定文档契约

- 在起草前，先识别目标读者、文档目的、文档类型、所需结构、语气以及证据标准。
- 如果用户已经提供开头、标题体系或格式模式，除非用户明确要求重写，否则尽量保留。
- 优先从请求中推断外部读者是谁，例如"导师""客户""评审"或"团队"，而不是把读者写成"用户"。

### 2. 把源材料和最终成文分开

- 把先前消息、笔记、草稿碎片和工作文本都视为源材料，而不是最终文稿本身。
- 从这些材料中提取事实、论点、约束和引文。
- 不要把工作过程中的提示语、批注语或修改痕迹直接带入最终文档。

### 3. 从零重建最终文档

- 把最终文档写成一份全新的成品，而不是在旧稿上做"修修补补"的痕迹性修改。
- 不要把句子写成"对原文的修正说明"。
- 除非用户明确要求变更说明、审稿备忘录或修订记录，否则不要提及早期版本的存在。
- 优先使用稳定、直接的陈述式表达，而不是过程叙述。

### 4. 清除备忘录式泄漏

- 最终文档绝不能读起来像笔记、审阅意见或和用户的对话。
- 不要保留类似这些表达：
  - "原先/前文/上文/这里/下面需要说明"
  - "我认为/我建议/我修改为/我补充了"
  - "这一点需要校正/这一类不准确"
  - "根据前面的调查/根据上面的修改"
  - "这里保留/这里删除/这一段应改为"
- 把面向修订过程的表达改写成面向读者的最终表达。
- 反例："原先的'行为感知增强'不够准确，这里改成曝光反事实增强。"
- 正例："曝光反事实增强以系统曝光序列为对象，通过替换曝光项并预测反馈来构造新的训练序列。"
- 不要当反驳型人格。最终读者没有看过旧稿，不知道你在反驳什么。

### 5. 病句功能分类

不要依靠禁用词表。判断一句话在文档中的实际功能。换词但保留同样功能，仍然不合格。

对每一句先问：

> 这句话在消除什么误解？这个误解读者会从哪来？

答不出读者来源，就删。

下列功能默认清除。

- **过程泄漏**：对话回应、修改说明、调查过程、作者备忘、内部 TODO、审阅口吻。
- **无源否定**：否认一个文中未建立、读者也无理由期待的对象。典型细句：`这不是 X，而是 Y`、`这些能说明 A，不能说明 B`、`并不是框架`。
- **无端假设**：引入当前读者任务里不存在的身份、环境或情景。
- **预防式前提**：为尚未出现的误解做铺垫、提醒或声明。典型细句：`需要特别说明的是`、`为避免混淆`、`值得一提的是`。
- **无端转折**：先造一个文中不存在的对立面再推翻。

定位线索（只用来找句子，不是准许这么写）：`无需`、`不会`、`注意`、`然而`、`虽然`、`如果`、`不是`、`而是`、`但是`。命中后必须做语义判断；词面本身不是删除理由。成稿默认不要用 `不是…而是…`、`但是` 这类对比句；有差异就直接写实际内容和范围。

否定句并非一律删除。只有同时满足以下条件时才保留：

1. 读者有合理理由预期相反行为。
2. 该差异会影响理解、结论、安全、范围或采用决策。
3. 材料中的证据足以支持该结论。
4. 文中说明了具体后果、范围或可执行的替代。

不能说明的内容直接不写，不要先立一个靶子再否定它。

### 6. 保持面向读者的结构一致

- 确保所有章节在语气、时态和正式程度上保持一致。
- 保证标题、表格、分类体系和术语在全文中前后一致。
- 如果文档建立了某种分类法，后续部分必须严格沿用，不要中途变口径。
- 如果是在续写现有草稿，要匹配它已经显露出的格式，而不要中途切换成另一套文风。

### 7. 像最终成文一样处理证据

- 只有在原文措辞本身非常重要时才使用引文。
- 优先选择能够支撑核心论点的引文，而不是偶然性的措辞。
- 每段引文都要通过上下文说明其意义，而不是孤零零摆在那里。
- 如果文档属于学术或分析型文档，要在引文后立刻说明它如何支撑论证。
- 涉及引文用法时，阅读 [references/final-deliverable-checklist.md](references/final-deliverable-checklist.md)。

### 8. 写后审计（阻断交付）

起草写入文件或准备交付正文后，文档不算完成。必须另开一轮，只删改，不扩写。

1. 如果正文在文件里，用 Read 把成稿再读一遍；如果直接输出，先把全文作为成稿重读。没读回，不得交付。
2. 按句扫描「病句功能分类」。每处只能：删 / 改成正面陈述 / 保留。保留必须指出读者会从哪产生相反预期。
3. 再执行 [references/final-deliverable-checklist.md](references/final-deliverable-checklist.md)。这份检查表每次交付都要做，不是长文档才做。
4. 扫描到的功能异常句必须当场改回文件或替换待交付正文，然后再读一轮核对已经是改后文本。只在回复里写「改写」「删除」、只在心里改、把修改留给别人，都算未完成。审计结论必须和正文一致。

不要把读回过程、抽查记录或修改说明写入面向读者的文档。

## 输出规则

- 优先输出完整章节，而不是"关于这些章节的说明"。
- 优先使用融为一体的成文表达，而不是"纠错式语言"。
- 如果用户要的是最终文档本身，就直接输出文档内容，而不是在外面再包一层说明。
- 如果确实需要补充说明，把说明放在最终文档之外。
