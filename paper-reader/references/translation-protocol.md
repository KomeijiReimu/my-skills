# 逐句翻译协议

只有在本轮包含翻译任务，且需要对英文论文做中文翻译时，阅读本文件。

## 核心原则

- 翻译不是概述。
- 翻译不是总结。
- 翻译不是改写。
- 翻译不是润色。
- 翻译不是提炼。
- 翻译不是讲解。
- 翻译不是"作者做了什么、说明了什么"的结果复述。

任务是把原文一句一句转成中文，而不是把一段话理解后再重新讲一遍。

把译文想成一份可以直接交给任何第三方读者的正式文件，而不是写给当前用户的工作说明、速记稿或便于自己理解的整理稿。

## 强制工作流

### 1. 按段落顺序处理

- 先读一个原文段落。
- 只处理当前段落，不要跳到后面的段落。
- 当前段落翻译合格后，再进入下一段。

### 2. 先识别句子边界

- 先明确这一段原文有几句。
- 心里建立"第 1 句、第 2 句、第 3 句……"的对应关系。
- 译文必须按同样顺序覆盖这些句子。

### 3. 先建立章节清单

- 在开始整篇翻译前，先从论文内容中记下章节和小节编号顺序。
- 至少核对所有带编号的标题，例如 `1`、`2.1`、`4.2.3`、`5.4`。
- 翻译过程中，每完成一个章节或小节，就回到这份清单确认没有跳过。

### 4. 采用句子分行格式

- 每个中文句子单独成行。
- 同一段中的多句译文，按原顺序连续排列。
- 段落之间空一行。

这个格式的目的不是美观，而是强制保留句子级对应关系，防止把整段压缩成概述。

### 5. 段落完成后立刻自检

在进入下一段之前，强制检查下面这些事：

- 原文每一句是否都有对应译文
- 是否把两句或多句压缩成一句
- 是否写成了总结、概括、评价、解释或讲解
- 是否漏掉了例子、限定条件、数字、比较关系、结论或解释句
- 是否因为追求"中文更顺"而把原文改写成另一种表达

如果任一项答案是否定的，就立即重写当前段落。

### 6. 文件完成后运行校验脚本

完成当前翻译文件后，运行：

```bash
python3 ~/.config/opencode/skill/paper-reader/scripts/validate_translation_output.py 论文stem.translation.zh.md
```

如果脚本报告了"方法概览""实验结论""作者发现""这说明"等可疑表达，或提示缺少章节编号，不要辩解，先回到文件中重写或补齐相关段落。

## 参考文献处理

- 到达 `References`、`Bibliography` 等参考文献部分时，不翻译条目内容。
- 保留原始参考文献条目即可。
- 不要把参考文献条目改写成中文说明。

## 明确禁止的错误

- 把一整段改写成几条中文要点
- 把"方法 + 结果 + 解释"压缩成一句结论
- 用"作者发现……这说明……"替代原文的逐句展开
- 先理解段意，再按自己的话重新组织成更短的中文摘要
- 把原文翻译写成"更适合中文读者"的润色稿
- 在翻译文件里夹带分析、评价或研究解读
- 把译文写成面向用户的"我来帮你理解论文"
- 漏掉某个章节、小节或子小节，例如把 `4.2.3` 整段跳过去

## 反例与正例

反例：

```text
作者比较了两种方法，发现新方法表现更好，这说明它学到了更好的表示。
```

这是一句概述，不是翻译。它把多句原文压缩成了一句解释性结论。

正例要求：

- 原文第一句说什么，译文第一句就对应翻出来
- 原文第二句补充什么，译文第二句就继续补出来
- 原文第三句给出数值，译文第三句就保留数值和比较关系

如果读者只能从译文里看出"这一段大意是什么"，那它就是不合格的。

## 最低合格标准

对于任一原文段落，读者应该能从译文中看出：

- 第一句在说什么
- 第二句在补充什么
- 第三句在解释什么
- 后续句子分别承担什么作用

如果译文只能让人看出"这一段大意是什么"，那它就是不合格的。

## 快速自问

在保存当前段落前，问自己：

- "我现在写的是翻译，还是转述？"
- "我有没有把原文的若干句压缩掉？"
- "我是不是为了顺口而把原文改写了？"
- "如果把原文和译文放在一起，能否大体句句对应？"

只要觉得自己更像是在"讲解原文"，就说明没有在翻译。
