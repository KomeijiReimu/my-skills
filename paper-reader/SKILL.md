# 论文精读

## 概述

对一篇或多篇学术论文进行完整阅读，产出逐句中文翻译和/或详尽中文解析。

支持三种工作模式：
- 只翻译
- 只解析
- 同时翻译与解析

用户可以自由选择任意模式。若用户未明确指定，默认同时翻译与解析。

## 工作流

### 1. 盘点全部输入论文

- 确认每个论文文件的准确路径。
- 建立检查清单，确保没有任何一篇被遗漏。
- 使用内置文件读取能力直接读取 PDF，无需依赖外部工具链。
- 只有当全部用户输入论文都被处理完毕，或被明确标记为阻塞时，才能声称任务完成。

### 2. 判定本轮模式

- 如果用户只要求翻译 → 执行"只翻译"。
- 如果用户只要求解析 → 执行"只解析"。
- 如果用户同时要求翻译和解析，或未明确指定 → 执行"同时翻译与解析"。
- 同时翻译与解析时，建议先完成翻译再做解析，因为翻译过程中建立的逐句理解有助于产出更准确的解析。

### 3. 验证文件可读性

- 使用内置工具直接读取 PDF 文件内容。
- 如果文件无法打开或内容无法提取，立即告知用户并说明问题。
- 绝不能对一个实际上无法读取的文件假装已经完成阅读。
- 如果抽取结果乱码、缺失或严重错位，明确告知用户并请求更好的源文件。

### 4. 完整阅读论文

- 按顺序从标题读到最终附录，不要跳读。
- 保留章节层级来阅读与理解内容。
- 有意识地检查图、表、算法、列表、图注、脚注和公式，想尽办法提取阅读这些内容，并明确告知用户
- 阅读图注时，要同时对照前后正文，不要只看图注本身。
- 如果内容不足以支撑可靠阅读，明确告知用户，不能脑补缺失内容。

### 5. 翻译模式

只要本轮包含翻译任务，就对每篇英文论文在当前工作目录生成一个 Markdown 翻译文件。

文件名：`论文文件名stem.translation.zh.md`

#### 翻译核心要求

- 把翻译文件当作面向第三方读者的正式交付物，不是工作笔记。
- 由模型在完整阅读和理解全文后直接完成翻译。
- 任何时候都不要编写、调用或依赖脚本、CLI、批处理程序或外部翻译服务来生成译文。
- 不要对原文做任何转述、总结、改写、润色、美化、提炼、解释或讲解。
- 翻译文件里不要夹带分析、评论、评价、归纳或"这说明……"之类的解析性句子。

#### 逐句翻译协议

- 必须逐字逐句、逐句对应地翻译整篇论文正文。
- 译文必须和原文句子顺序一一对应。原文有几句，译文就必须覆盖那几句，不能把多句压缩成一句总结。
- 不要把整段内容改写成"作者发现……这说明……"之类的摘要式表达，除非原文本来就是这样写的。
- 必要时可以为了中文通顺拆句或合并极短的并列短句，但不得丢失任何一句原文所承载的信息点。
- 如果某一段原文包含例子、限定条件、数值、对比、结论和解释，这些内容都必须在译文中逐句落实，不能只保留结论。

#### 翻译格式

- 按原文章节顺序逐段翻译。
- 每个译文句子单独成行。
- 段落之间留空行。
- 在正式翻译前，先根据论文内容列出章节和小节清单，尤其要记录带编号的节、小节和子小节（如 `4.2.2`、`4.2.3`、`4.3`）。
- 在进入下一段之前，先做一次句子级自检：确认本段没有漏句、没有把多句压成一句、没有改写成总结。
- 如果发现自己已经写成概述、提炼、归纳、润色稿、结果复述或论文讲解，必须立即重写该段。

#### 保留结构

- 保留标题层级、列表、图表标题、脚注、附录标题、算法步骤和公式编号。
- 公式、符号、变量名、引文编号和引用键默认保持原始记法。
- 参考文献一栏不用翻译。到达 `References`、`Bibliography` 等参考文献部分时，保留原始条目。

#### 翻译禁止行为

- 不得总结代替翻译。
- 不得压缩整段含义。
- 不得省略重复段落。
- 不得跳过附录。
- 不得用意译掩盖难句。
- 不得把"原文翻译"写成"论文讲解"。
- 不得使用脚本、CLI、批处理程序或外部翻译服务生成译文。
- 不得翻译参考文献条目。

#### 翻译文件头部

在文件开头附近注明：
- 源文件路径
- 论文标题（如果能够可靠识别）
- `模式：翻译`
- "本文件为完整中文翻译"的简短说明

#### 翻译自检

每完成一个翻译文件，运行校验脚本做总结式漂移和章节覆盖检查：

```bash
python3 ~/.config/opencode/skill/paper-reader/scripts/validate_translation_output.py 论文stem.translation.zh.md
```

只要校验脚本报错，就先修正当前翻译文件，再继续下一篇论文。

如果有源抽取稿可用，可加 `--source` 参数做章节覆盖对比。

#### 翻译快速自问

在保存每个段落前问自己：
- "我现在写的是翻译，还是转述？"
- "我有没有把原文的若干句压缩掉？"
- "我是不是为了顺口而把原文改写了？"
- "如果把原文和译文放在一起，能否大体句句对应？"

只要觉得自己更像是在"讲解原文"，就说明没有在翻译。

### 6. 解析模式

只要本轮包含解析任务，就对每篇论文在当前工作目录生成一个 Markdown 分析文件。

文件名：`论文文件名stem.analysis.zh.md`

#### 解析覆盖要求

分析必须覆盖整篇论文，不能只写摘要和方法部分。至少说明这些内容：

- 文献信息（标题、作者、发表场所、年份）
- 问题设定与研究动机
- 前提假设与问题形式化
- 符号体系与关键定义
- 方法流程（完整描述，不是概述）
- 目标函数、损失项与优化细节
- 算法步骤
- 训练设置与实现线索
- 数据集与预处理
- 基线方法与评测协议
- 主要结果（含关键数值）
- 消融实验与敏感性分析
- 重要图表的含义和作用（用中文解释）
- 附录内容
- 局限性与风险
- 复现线索
- 开放问题与未来方向

#### 解析质量要求

- 说明每个章节如何支撑论文整体论证。
- 优先追求完整性，不要为了简洁牺牲覆盖面。
- 用中文解释所有重要图表的含义和作用。

#### 解析文件头部

在文件开头附近注明：
- 源文件路径
- 论文标题
- `模式：解析`

### 7. 严格处理多篇论文

- 可以逐篇处理，但必须维护一份全局检查清单，确保整批论文全部覆盖。
- 除非用户明确要求比较报告，否则每篇论文分别输出结果。
- 不得因为某篇论文与另一篇相似，就默默跳过它。
- 论文数量多时，也必须一次性持续处理到整批任务全部完成；不能因为篇数多、内容长或已经完成部分结果，就自行在中途收尾。
- 在整批任务结束前，可以逐篇推进并写出中间文件，但不能把"已完成部分论文"表述成"任务完成"。
- 只有在用户明确中止、环境阻塞无法继续，或源文件本身存在不可恢复的问题时，才能停止整批处理。
- 如果某篇论文因文件损坏而阻塞，要明确指出是哪一篇、为什么阻塞。

## 输出约定

- 翻译文件和分析文件可以在同一轮中同时输出。
- 翻译文件应当让未参与本轮对话的第三方读者直接阅读，不得出现"我来说明""下面总结""这里我们看到"这类对话式或讲解式语气。
- 文件名使用源文件 stem，保持稳定可追踪。
- 输出结构要足够清晰，方便用户从结果快速定位回原论文。
- 在每个生成的 Markdown 文件开头附近注明源文件路径。
